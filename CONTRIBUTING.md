# Contributing to OpenToolHub

Thanks for being interested in OpenToolHub.

We are building a practical project for discovering public tools by real-world use case and stack. Contributions are welcome as long as they are useful, clear, and grounded in actual product thinking.

## Ways to contribute

You can contribute in several ways:

- suggest a new use case
- propose a stack recommendation
- add a starter template or example
- improve documentation and onboarding
- share a practical workflow that uses public tools
- help refine the project story and positioning

## What makes a good contribution

Strong contributions usually do one or more of these things:

- explain a real problem or product idea
- connect the idea to relevant tool categories
- show how tools fit together in a stack
- provide a clear example or starter path
- help other builders move faster

## Contribution style

The project values clarity over hype.

Please keep contributions:

- practical
- specific
- easy to understand
- grounded in real builder needs
- distinct from copied or generic boilerplate

## Suggested workflow

1. Pick a use case, problem, or stack idea.
2. Write a short explanation.
3. Add key categories and how they fit together.
4. Share why the combination is helpful.
5. Open a pull request or issue with your contribution.

## Project principles

We aim for:

- real usefulness over vanity
- simple and clear docs over clutter
- original thinking over imitation
- practical product value over empty hype

## Before you open a pull request

Data changes are only useful if they validate. Run the same checks CI runs:

```bash
python3 scripts/validate.py --strict
python3 -m unittest discover -s tests -v
python3 scripts/build_site.py
python3 scripts/build_site.py --check
```

If you changed a page or module, preview it with:

```bash
python3 scripts/build_site.py --serve
```

Then load <http://127.0.0.1:8000/> and follow the links you touched. Mention the
commands you ran in the pull request description.

### Data changes

- Read [docs/data-model.md](docs/data-model.md) before editing JSON.
- Keep reciprocal references valid: a use case lists its stack and templates,
  and each stack or template lists the use case back.
- Do not add an API without an official `url` and `docs_url`.
- Do not describe pricing, licensing, or availability you have not checked.
- Do not commit `site/data/`; it is generated by `build_site.py`.

### Runnable starters

Most templates are design briefs that end at `README.md`. A template may also
ship a working app in the same folder, which means it must stay runnable by
someone who just cloned the repository:

- Keep the layout: `app/` for the code, `scripts/` for data refresh, `tests/`
  for the checks, plus a `Makefile` with `serve`, `test`, and `fetch` targets.
- No dependencies, no keys, no backend, no build step. If the app needs data,
  commit a snapshot and let a script refresh it, as
  [public-data-dashboard](templates/public-data-dashboard/README.md) does.
- Keep logic that can be tested separate from DOM access, so the tests can call
  pure helpers directly instead of simulating a whole page.
- Cover the failure paths too: a missing snapshot, a bad query string, an
  empty selection.
- Run the Node suites before opening the pull request; CI runs them as well:

```bash
make starter-test
```

## Questions or ideas


If you are unsure where to start, pick a use case and propose a stack or a starter template. That is often the easiest and most valuable contribution.

We are glad to have you here.
